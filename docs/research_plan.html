Overarching scientific question

When adapting a pretrained vision model to scientific images collected across acquisition environments, is a fixed parameter budget better allocated as shared dense capacity or sparse input-conditional capacity?

Experimental setting

Isolate the moment of scientific adaptation

DINOv2 has not previously learned from the target scientific dataset. Dense and sparse models encounter the scientific domain for the first time during the same supervised fine-tuning stage.

Common start

Pretrained DINOv2

Identical encoder checkpoint, target classification head initialization, preprocessing, data order, and seed.

→
Two branches

Dense-wide or upcycled MoE

Convert the selected FFN before exposure to scientific training data, then fully fine-tune every parameter with pooled ERM.

What “full fine-tuning” means

  • All encoder and task-head parameters are trainable.
  • Training uses standard supervised cross-entropy.
  • Training examples pool the observed acquisition environments.
  • Batch or hospital identity is not used by the core model.
  • OOD validation selects recipes; OOD test remains untouched.

What this is not

  • Not linear probing or parameter-efficient fine-tuning.
  • Not dense scientific fine-tuning followed by later upcycling.
  • Not unsupervised adaptation to the held-out test environment.
  • Not a batch-correction preprocessing paper.
  • Not a general domain-generalization leaderboard study.
Resource control

Fix the capacity budget—and name the remaining tradeoff

No single dense model can simultaneously match an MoE’s stored parameters and its sparse active computation. The primary experiment fixes total trainable parameters; active compute is reported as a second resource axis.

Model Total parameters Active FFN compute What it identifies
Dense-wide Fixed budget P* All widened units Primary fixed-total-parameter comparator
Learned top-1 MoE Fixed budget P* One expert per decision Conditional allocation of the same capacity
Frozen-router MoE Same MoE architecture Same as learned MoE Whether learned assignments add value
Original dense Lower total P₀ Approximately MoE-active Secondary accuracy–compute reference
conditional gain = OOD(learned MoE) − OOD(depth-matched dense-wide)
routing gain = OOD(learned MoE) − OOD(frozen-router MoE)

Function-preserving initialization

Every expert begins as a copy of the pretrained FFN. The widened dense FFN contains repeated copies whose output projection averages their contributions. Dense-wide, learned MoE, and frozen-router MoE therefore compute the same function at initialization.

W₁(wide) = [W₁; … ; W₁]    and    W₂(wide) = [W₂, … , W₂] / E
Exact accounting rule. Choose the closest realizable dense width after counting the router, predeclare a tolerance below 0.1%, report exact counts, and do not pad either model with unused parameters.
Optimization fairness
Report a matched-recipe comparison with identical optimization settings, plus an equal-search-budget comparison in which dense-wide and MoE receive the same small learning-rate search. Use paired seeds and identical data order wherever possible.

Why the comparisons are non-obvious

Image routing

Global stain, scanner, illumination, or experiment appearance may call for a global calibration expert. Yet the same mechanism may memorize known batches and fail on an unseen environment.

Token routing

Local routing can specialize on cells and tissue structures, but it may fragment globally coherent acquisition variation and creates many more routing decisions.

Early routing

Early features expose acquisition appearance directly. This can create a shortcut, or enable early conditional correction followed by shared recombination.

Middle routing

Middle layers may be the first point where acquisition and task structure are both separable, while enough shared computation remains to integrate expert outputs.

Late routing

Late features contain more task structure, but little shared computation remains to reconcile expert-specific representations before prediction.

Parameter-matched router geometry

Linear and cosine routers must share the same E × d weight matrix and temperature. Cosine routing normalizes the input and router rows; it does not receive an additional learned projection.

linear: rₑ(x) = wₑᵀx / τ     cosine: rₑ(x) = ⟨wₑ/‖wₑ‖, x/‖x‖⟩ / τ
Batch-effect intuition, with an important caveat. Linear routing can use feature magnitude and permit high-norm router rows to dominate; cosine routing turns the router into angular prototype matching. This may reduce norm-driven batch partitioning, but the ViT sends LayerNorm-normalized features into its FFN, so cosine routing is not automatically batch invariant. The study must measure whether feature norm, acquisition intensity, or feature direction actually predicts the routes.

Pressure location is a three-level scientific factor

The question is not simply whether to “remove batch.” It is where acquisition information may be useful and where it becomes harmful. Compare three mutually interpretable policies across every architecture cell:

Policy Route objective Final embedding Scientific hypothesis
Canonical Global load balancing No explicit invariance Ordinary conditional adaptation can decide how to use acquisition information.
Route-level Within-environment load balancing No explicit invariance Preventing an environment from monopolizing experts improves transferable routing.
Output-level Global load balancing Batch-adversarial final representation Routes may use acquisition context internally, but predictions benefit when it is removed downstream.
12 architectures × 3 pressure policies = 36 MoE configurations per dataset
canonical MoE: L = L_task + λ_z L_z + λ_lb L_global-balance
route-level: replace L_global-balance with L_within-environment
output-level: L_canonical + λ_inv L_batch-adversarial(final embedding)
L(within-environment) = mean over e of L_balance({ soft routes i : environment(i) = e })

The router z-loss is a fixed numerical-stability term, not a scientific factor. Here “environment” means the acquisition batch or hospital, not the stochastic minibatch. Within-environment balancing replaces global balancing rather than stacking on top of it. The combined route-level + output-level policy is not in the primary grid: it answers an interaction question beyond the clean “where should pressure act?” comparison.

Fairness controls. Estimate the within-environment objective with an environment-balanced sampler or per-environment moving usage statistics. Use that same sampler for the canonical arm. Apply the same output-invariance objective to the depth-matched dense-wide model. The adversary is a training-only linear head with fixed capacity and schedule. Count its parameters and compute separately; the inference parameter budget remains P*.
Where the combined and no-load-balancing conditions go
Run no-LBL only as a collapse diagnostic on a preregistered design-cover subset. If both route-level and output-level policies improve the same architecture family, test their combination on that same subset. Neither condition participates in primary factor-effect claims.

Empirical scope

Two co-primary datasets, two acquisition regimes

Run the entire 36-cell grid on both datasets. Their value comes from complementary acquisition structures—not simply from having many images.

RxRx1

Experimental-batch shift

Fine-grained multiclass cellular morphology with many experimental batches. RxRx1 carries the strongest environment-level and mechanistic inference.

  • Use repeated leave-experiment-out development folds.
  • Bootstrap uncertainty by experiment, not image.
  • Condition batch analyses on perturbation label.
Camelyon17

Hospital-site shift

Binary tumor classification under staining, scanner, and hospital variation. Camelyon tests whether factor effects cross modality and acquisition regime.

  • Run the same grid without dataset-specific architecture changes.
  • Aggregate uncertainty by patient or slide, not patch.
  • Treat hospital-level generality as limited by the small site count.
Claim boundary. The study can establish controlled findings across two scientific imaging settings. It cannot establish universal principles for all scientific foundation-model adaptation.
OOD gain ~ placement × routing unit × router geometry × pressure policy × dataset

Consistent factor effects support a transferable design principle. Dataset-specific effects remain valuable only when the routing and representation analyses explain why the acquisition regimes behave differently.

Before the scientific grid

Tune the protocol without tuning away the experiment

Hyperparameter optimization cannot prove that every cell is globally optimal. The defensible target is narrower: a symmetric search, performed only on development environments, that produces a stable shared recipe before factor comparisons begin.

Core rule. Hyperparameters may differ by dataset and by loss family, but not by placement, routing unit, or individual architecture cell. Independently tuning all 36 cells would turn search luck into an apparent factor effect.

1. Establish three data boundaries

Boundary Used for Never used for
Inner OOD folds Optimizer, router temperature, and loss-weight calibration Headline architecture selection or final claims
Official OOD validation Full factorial comparison, model-family selection, frozen contrasts Repeated coefficient adjustment after seeing grid results
Official OOD test One confirmatory evaluation of the frozen comparison set Tuning, debugging, early stopping, or choosing analyses

Construct inner folds only from official training environments: leave experiments out on RxRx1 and rotate the available training hospitals on Camelyon17. Keep all samples from an experimental batch, patient, or slide on one side of a fold. Because Camelyon has few hospitals, report every fold rather than treating patches as independent replications.

2. Use a fixed design-cover calibration panel

Choose the panel before looking at grid results. It should expose the optimizer to dense and sparse models and cover the factor levels without becoming a miniature model search:

Dense-wide · middlePrimary comparator
Early · image · linearAcquisition-sensitive extreme
Middle · token · linearLocal conditionality
Middle · image · cosineAngular image routing
Late · token · cosineSemantic-routing extreme
Canonical pressureOptimizer calibration only

Select a shared dataset-level recipe by its mean rank across panel members and inner folds; break ties with mean OOD score. Do not select by the best single model. A recipe that helps one cell while destabilizing the others is rejected.

3. Tune in three bounded passes

Pass Search space Budget and selection rule What is frozen afterward
A. Full fine-tuning LR {3×10⁻⁵, 10⁻⁴, 3×10⁻⁴}; weight decay {0.01, 0.05, 0.1}; layer-wise LR decay {0.65, 0.8, 1.0}; drop path {0, 0.1, 0.2}; warmup {5%, 10%} Use 12 predeclared random or low-discrepancy combinations per dataset rather than the Cartesian product. Screen with one seed on the calibration panel; rerun the best three recipes with a second seed on every inner fold. One optimizer recipe and one maximum training horizon per dataset
B. Router calibration Temperature τ {0.03, 0.1, 0.3, 1.0}, separately for linear and cosine geometry; fixed z-loss coefficient Equal trial counts for both geometries. Choose one τ per geometry × dataset using the MoE members of the same panel. Two temperatures per dataset; no placement- or unit-specific τ
C. Pressure strength Normalized load-balance weight {10⁻³, 10⁻², 10⁻¹}; output-invariance weight {10⁻², 10⁻¹, 1} Equal-size log grids on the same panel. Use a fixed gradient-reversal ramp and select by task OOD score—not by minimum batch decodability. One λlb and one λinv per dataset

Normalize global and within-environment balancing so that their uniform-routing reference has the same scale. Then reuse the same λlb; otherwise a “location” effect is confounded with unequal regularization strength. Keep batch size, gradient accumulation, scheduler family, augmentations, sampler, precision, and checkpoint rule fixed across every cell.

Current-recipe anchor. Include the starter’s existing ViT recipe (AdamW, LR 10⁻⁴, weight decay 0.05, layer-wise decay 0.7, drop path 0.2, geometric random-resized crop) as one of the predeclared trials. Treat the current 90-epoch RxRx1 and 10-epoch Camelyon horizons as starting hypotheses, then verify plateauing on inner folds rather than assuming that either is already tuned.

Set the maximum horizon once per dataset using the current-recipe dense-wide pilot. If the inner-OOD curve has not plateaued during the final 20% of training, extend the horizon once by 2× and repeat. After that, freeze the horizon and number of optimizer updates for every model. Keep the effective batch size at 64 unless a documented memory limit requires gradient accumulation; token and image routing must still see the same examples and optimizer-step count.

Why augmentation is not ordinary HPO here
Color, stain, intensity, and style augmentation directly manipulate the batch effect being studied. Freeze one scientifically reasonable augmentation recipe before the grid. If desired, evaluate a strong photometric or stain augmentation as a separately named robustness baseline; do not silently select it during HPO.

4. Define “tuned enough” before launching the grid

Required checks

  • The winning value is not on a search boundary; otherwise expand once.
  • Neighboring settings give similar rankings, not a single isolated spike.
  • The selected recipe is stable across inner environments and the second seed.
  • Training and OOD-validation curves have plateaued before the horizon.
  • No model family is uniquely unstable under the shared recipe.

Failure policy

  • Log NaNs, expert collapse, out-of-memory events, and incomplete runs.
  • Use one predeclared retry with the same seed and configuration.
  • Do not replace a failed trial with a new hyperparameter draw.
  • Report failure rates by model family and pressure policy.
  • Expand a range once only when the best value lies at its boundary.

5. Report two fairness tracks

Track Purpose Recipe Claim it supports
Controlled factorial Interpret placement, unit, geometry, and pressure effects Shared frozen dataset-level hyperparameters Design principles and interactions
Equal-budget finalist audit Rule out an optimizer recipe that accidentally favors one model Selected MoE and matched dense-wide each receive the same small independent search budget on official OOD validation: eight low-discrepancy LR/decay trials centered on the shared recipe, with the best two repeated using a second seed Headline best-achievable dense-versus-sparse comparison
Do not merge the tracks. Use the shared-recipe results for the factorial analysis. Use the equally tuned finalist results only for the final performance contrast. Publish every trial and its selection rule.
Operational sequence

Audit, calibrate, explore, freeze, confirm, explain

The order is dictated by information access. Anything that sets optimization happens on inner folds; anything that chooses scientific contrasts happens on official OOD validation; the official tests are opened only after every choice is frozen.

Stage 0

Make the comparison executable and auditable

Implement the dense-wide and MoE branches, then verify all invariants before starting HPO.

  • Exact trainable and inference parameter counts within the 0.1% tolerance.
  • Dense-wide, learned MoE, and frozen-router outputs match at initialization.
  • Top-1 active expert count, routing unit, and chosen placement are correct.
  • RxRx1 and Camelyon use the intended transforms and identical input resolution.
  • All run IDs serialize every factor, loss policy, seed, and split.
Known implementation deltas in the current starter
The current defaults use eight experts with top-2 routing; the study requires top-1. The current cosine router includes an extra learned projection; replace it with the same E × d weight matrix used by the linear router. Add the function-preserving dense-wide comparator and frozen-router mode. Verify that the Camelyon transform actually respects its configuration flag. Finally, add explicit run fields for placement, routing unit, geometry, pressure policy, temperature, all loss weights, parameter counts, and data-split identity.
Stage 1

Calibrate shared hyperparameters on inner OOD folds

Execute the three bounded tuning passes in the previous section. Freeze a dataset-level optimizer recipe, geometry-specific router temperatures, and pressure coefficients. Archive the complete tuning table before running the grid.

  • No official OOD test access.
  • No per-cell optimizer or loss-weight tuning.
  • Expand a search range at most once, only under the boundary rule.
Stage 2

Run the joint development grid on both datasets

Train every architecture × pressure cell with three paired seeds on each dataset. Use the same seed to control initialization, data order, and augmentation draws across the relevant dense and MoE comparisons.

  • MoE grid: 36 × 2 datasets × 3 seeds = 216 runs.
  • Dense-wide: 3 placements × {canonical, output-invariant} × 2 datasets × 3 seeds = 36 runs.
  • Original dense reference: 2 datasets × 3 seeds = 6 runs.
  • Analyze main effects and predeclared two-way interactions, not only the winner.
Stage 3

Freeze the confirmatory comparison set

Use official OOD validation to select one cross-dataset MoE design, its depth-matched dense-wide model, its frozen-router counterpart, and one matched failure differing in exactly one factor. Select the shared design by mean standardized improvement over its dense comparator across datasets.

selection score = mean over datasets of standardized [OOD(MoE) − OOD(dense-wide)]

Record dataset-specific winners descriptively, but do not substitute them for the shared design in the main claim. Freeze all analyses, probe training splits, and counterfactuals now.

Stage 4

Run the equal-budget tuning audit

Give the frozen shared MoE and its dense-wide comparator the same small independent search budget on official OOD validation. Keep the controlled-grid checkpoints; this produces a second, clearly labeled performance track rather than rewriting the factorial study.

Stage 5

Run fresh-seed confirmatory test evaluation

Retrain the frozen comparison set with five fresh paired seeds and evaluate the untouched OOD tests once. Report paired differences and environment-clustered uncertainty, plus ID performance, worst-environment performance, parameters, active FLOPs, throughput, memory, and training cost.

Stage 6

Explain success and failure

Compare the selected MoE, frozen-router MoE, depth-matched dense-wide model, and matched failure using routing, layerwise representation, and counterfactual analyses.

Mechanistic payload

Analyses tied directly to the grid hypotheses

The mechanism section must explain why one factor combination generalizes and another fails. Attractive embeddings or routing maps alone are insufficient.

01

Expert utilization

  • Effective number of experts
  • Assignment entropy and load imbalance
  • Per-environment expert usage
  • Stability across seeds

Tests whether load balancing creates meaningful specialization or only distributes traffic.

02

Conditional route information

  • Batch/site information in routes conditional on label
  • Label information in routes conditional on environment
  • Per-image histograms for token routing
I(routes; batch | label)    and    I(routes; label | batch)
03

Layerwise representation change

  • Probe immediately before the modified block
  • Probe immediately after it
  • Probe the final CLS representation
  • Compare against the depth-matched dense-wide model

Localizes whether conditional computation amplifies, redirects, or suppresses acquisition information.

04

Router-geometry diagnosis

  • Feature norm versus router confidence
  • Image intensity/stain statistics versus assignment
  • Assignment change after feature normalization
  • Linear-versus-cosine OOD contrast

Directly tests whether magnitude-sensitive routing follows acquisition intensity.

05

Cross-environment task structure

  • Label probe trained on seen environments, tested unseen
  • Within-label cross-environment dispersion
  • Cross-environment nearest-neighbor retrieval
  • Batch decodability conditional on label

Establishes whether the final representation preserves transferable scientific signal.

06

Counterfactual rerouting

Keep trained expert weights fixed, replace learned assignments with balanced randomized assignments at evaluation, and measure the OOD loss.

route reliance = OOD(learned routes) − OOD(randomized routes)

This tests whether routing decisions causally contribute to the observed gain.

Visualization policy. Use one PCA panel to illustrate a result already established by conditional probes and cross-environment metrics. UMAP and token maps are supplementary illustrations, not evidence.
Result logic

What each possible outcome would mean

Observed result Scientific interpretation
Learned MoE > dense-wide and frozen router Learned conditional allocation is useful at a fixed capacity budget.
MoE > original dense but ≈ dense-wide The gain is attributable to added stored capacity, not conditional routing.
Learned MoE ≈ frozen router Sparse expert partitioning may matter, but the learned assignment policy does not.
Batch-decodable routes + batch-reduced final embedding + high OOD Environment-aware internal processing may be conditionally correcting acquisition variation.
Batch-decodable routes + batch-decodable final embedding + low OOD The router has created a batch-memorization channel.
Load balancing raises utilization but not OOD Balanced use is not equivalent to useful specialization.
Randomized rerouting leaves performance unchanged Router behavior is mechanistically incidental to the result.
Scope discipline

Keep the study systematic, not sprawling

Core paper

  • Two real scientific acquisition-shift datasets
  • Full fine-tuning from the same DINOv2 checkpoint
  • Fixed total parameter budget
  • 12 architectures × three pressure policies
  • Depth-matched dense-wide controls
  • Frozen-router confirmation
  • Routing and representation mechanism analyses

Not in the primary grid

  • Synthetic batch-strength or correlation sweeps
  • Expert-count and top-k sweeps
  • Multiple MoE-depth budgets
  • Extra router projections or custom routers
  • Expert-specific invariance modules
  • Per-cell optimizer or loss-weight tuning
  • Combined route + output pressure in the full grid
  • Multiple backbone families
  • Specialized CNNs as primary comparators
One permitted targeted follow-up. If routing becomes batch aware, and both route-level and output-level pressure help on their own, combine them on the preregistered design-cover subset. This tests whether the two mechanisms are additive, redundant, or antagonistic without creating a fourth pressure level across all architectures.
Community value

What makes this an ICLR paper

The value is not merely performance on two biological datasets. The study asks how a general-purpose pretrained model should allocate a fixed adaptation budget when the specialist domain contains both scientific signal and strong measurement variation.

Contribution 1

A function-preserving, fixed-total-parameter comparison of dense and sparse scientific adaptation, with active compute reported separately.

Contribution 2

A compact design map identifying how routing depth, spatial scale, and similarity geometry interact with the location of batch-invariance pressure under real acquisition shift.

Contribution 3

A mechanistic account connecting expert assignments, layerwise representation change, and generalization to unseen acquisition environments.

Success bar

A stable factor-level design principle plus a mechanism. One winning cell with noisy routing visualizations is not enough.

The success of sparse adaptation under acquisition shift depends on whether routing operates at the appropriate spatial scale and representation depth, whether its similarity geometry favors transferable structure, and where batch invariance is imposed.

Working hypothesis—not a promised result. A controlled negative finding remains meaningful if it identifies a reproducible routing failure mode.
